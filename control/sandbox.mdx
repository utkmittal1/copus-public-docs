The sandbox is a boundary macOS holds around every task Copus runs. A task writes only inside its own folder and the folders you added to it. In your home folder, it reads only its own folders, the folders you added, the files you attached, and your Desktop, Documents, Downloads and Pictures folders. A task can also reach the network.

macOS enforces that boundary. Copus hands macOS the list of what a task may write and read, and macOS applies that list to the program it starts and to everything that program starts after it: a file tool, a command, a script Copus wrote and ran, a helper that script launched. macOS holds this boundary whatever program runs inside it.

This page covers how to:

- [Find the folders a task can write to](#what-a-task-can-write), and the few places outside them
- [Learn which filenames no task can write](#files-no-task-can-write), anywhere on your Mac
- [See what a task can read](#what-a-task-can-read), and which folders stay shut
- [Understand why writing is confined and reading is not](#why-copus-confines-writing-and-not-reading)
- [Know where the sandbox stops](#where-the-sandbox-stops), and what covers the rest

<Note>
  Copus starts a task only when macOS can apply the sandbox to it. If macOS can't, Copus refuses to start the task.
</Note>

## What a task can write

A task writes inside its own folder, which depends on where the task sits. A conversation can also write in the folders you add.

- A conversation outside a project writes inside its own workspace folder, and your other files stay as they are. A task Copus starts on its own writes inside its own workspace folder in the same way.
- A conversation in a project writes anywhere inside that project's folder, because tasks in a project are meant to build on each other's files. For a project you pointed at a folder of your own, that means your folder. Copus creates files in it, and writes over files you already had.
- A conversation also writes inside each folder you added to it or to its project. See [Add a folder Copus can change](/concepts/sessions-and-workspace#add-a-folder-copus-can-change).
- A multi-step task and a scheduled task write inside the folder that task belongs to. A task outside a project gets a folder of its own, shared by every step or run. A multi-step task inside a project writes inside the project's Copus folder. For a project Copus manages, that's the whole project folder. For a project you pointed at a folder of your own, it's the subfolder Copus created there, so your own files around it stay out of reach. A multi-step task also writes in the folders it took from its conversation when the conversation switched to multi-step. A scheduled task never gets a folder you added.

To find where each folder sits on disk, see [Tasks and the workspace](/concepts/sessions-and-workspace).

A task can also write to a few places outside its folder. Copus gives each task a temporary folder of its own for scratch work. A task can't write to the Mac's shared temporary folders, such as `/tmp`. Claude Code and Codex each keep a configuration folder, where they write state as they run and renew their own sign-in. Copus's browser keeps two folders, one holding the logins for sites you have signed in to and one holding its own working files. Copus leaves the browser program itself unwritable, so a task can't replace the program that browses for it.

<Note>
  Copus points Python's package installer at a `.python` folder inside the task's own boundary, so a task can install a package it needs and the install lands where its other files land.
</Note>

## Files no task can write

Copus blocks writes to these filenames everywhere, including inside the folder a task can otherwise write freely:

- `copus.db`, `copus.db-wal`, and `copus.db-shm`, the files of Copus's own database.
- `settings.json`, `settings.local.json`, and `CLAUDE.md`, which Claude Code reads when it starts. A task that could rewrite any of those files could hand itself permissions or standing instructions on its next run, so Copus blocks every write to them.

macOS matches those names on the filename alone, wherever the file sits. The rule covers every copy. A task can't create a file of its own called `settings.json`, even in its own folder. A task that tries gets an error.

## What a task can read

A task reads its own folder, the files you attach, and the folders you added to it. A task in a project also reads the project's folder, the folders you added to the project, and its sources. Every task can also read the files other tasks made. Every task reads your Desktop, Documents, Downloads and Pictures folders too, but can't write or change files in these folders unless you explicitly add a folder within these to your session or project. macOS shuts the rest of your home folder, such as `Movies`, `Library`, and the hidden folders whose names start with a dot. To let a task read another folder, add it to the task or its project. Copus can then change the files in it as well. Outside your home folder, a task reads the system and the programs you installed, but not other drives or the `/Users/Shared` folder. Copus reads without asking, and you can't set reading to ask.

macOS shuts these folders in your home folder to a task and to every process it starts: `.ssh`, `.aws`, `.azure`, `.gnupg`, `.kube`, `.docker`, `.gradle`, `.m2`, `.huggingface`, `.kaggle`, and `.config/gcloud` and `.config/gh`, the settings folders for the `gcloud` and `gh` command-line tools.

macOS shuts these files in your home folder too. `.netrc`, `.npmrc`, `.pypirc`, and `.git-credentials` hold credentials outright. Your shell startup files, `.zshrc`, `.zshenv`, `.bashrc`, `.bash_profile`, and `.profile`, routinely hold an exported API key.

macOS also shuts Copus's own database, under a separate rule.

<Note>
  macOS binds the block to every process the task starts, as well as to Copus's own tools. A task can't get around it by asking a command-line tool to print a key.
</Note>

Copus asks you before a task reads a credential file anywhere else on your Mac, such as an `.env` file, a `.pem` or `.key` file, an `id_rsa` key file, or a file named `credentials.json`, `auth.json`, or `secrets.yaml`. Copus reads a template such as `.env.example`, `.env.sample`, or `.env.template` without asking. Copus also asks before a task reads your keychain folder or the sign-ins Copus keeps in `CopusData`. Copus asks every time, in every approval mode, and waits for your answer. For every name, and for what happens when nobody is there to answer, see [Approvals and permissions](/control/approvals-and-permissions).

<Warning>
  The shut folders and files are the places credentials usually sit. A secret can live in a file with any name, in any folder, so the list can't cover every secret. The list stops a task from reading a token by accident while it looks around. Treat the list as a guard against accidents rather than as a guarantee.
</Warning>


## Why Copus confines writing and not reading

A task has to read your own material to do your work. A document you attached to a message, a spreadsheet in your Downloads folder, and a report in your Documents folder all sit outside the task's own folder. If Copus confined reads to that folder, a task could write files and still couldn't read the files you asked it about. So every task can read your Desktop, Documents, Downloads and Pictures folders, and you add any other folder a task needs.

Copus puts each limit where a task could do damage. Writing is where a task can destroy something, so Copus confines writing to the task's own folder and the folders you add. Reading is where a task can leak something, so macOS shuts the rest of your home folder and the credential folders, and Copus asks you before a task reads a credential file anywhere else.

## Where the sandbox stops

The sandbox controls where a task may write and what it may read. It also keeps a task away from your keychain and your other apps. A task can't ask macOS for a keychain value, open or control another app, read the clipboard, use the microphone, read your Mac's Calendar or Reminders, ask for your location, or start a program that keeps running after the task. It also can't stop a program it didn't start, such as one of your apps, Copus itself, or another task. It can't mount, unmount or eject a disk, run one of your Shortcuts, or use the SSH keys your Mac's SSH agent holds. The cases below fall outside the sandbox.

**The network is open.** A command a task runs can reach the internet. Copus controls that by asking before every command outside its read-only list, which is why you can't set **Run commands** to run on its own. On **Autopilot**, Copus answers that question itself.

**A refused write fails quietly.** macOS refuses the write and hands the task an error. Copus doesn't ask you about the write, so you can't approve it by mistake. Copus either reports the failure in its reply or works around it.

**One task can read another task's files.** A task can read the files any other task made, so treat anything a task produced as visible to a later task. It can't change them unless both tasks are in the same project.

**Tasks in the same project can write each other's files.** They share the project folder by design. A task outside a project can still read another task's files, and can't write them. Two conversations you added the same folder to can both write in it.

**A key you hand a program yourself can be read.** A task can read the settings any program on your Mac started with, so a key you export in a Terminal window is readable while that program runs. You can use [Secrets](/connections/secrets) to securely store and use passwords, tokens, and API keys in Copus.

**Copus protects a stored credential by other means.** Copus keeps the value out of the conversation. See [Secrets](/connections/secrets).

<Note>
  Skills are the packaged instructions Copus follows for particular kinds of work. A task can read and follow a skill from anywhere, and can never rewrite it.
</Note>
