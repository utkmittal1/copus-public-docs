The sandbox is a boundary macOS holds around every task Copus runs. A task writes only inside its own folder and the folders you added to it. In your home folder, it reads only its own folders, the folders you added, the files you attached, and the folders on your [**Folders Copus can read**](/working/tools#see-what-copus-can-do-with-no-app-connected) list. That list starts with your Desktop, Documents, Downloads and Pictures folders. On the internet, a command a task runs reaches only the websites Copus lets through. In a project or AI team set to **Coding**, a task can read most of the rest of your Mac too, so it can work on code.

macOS enforces that boundary. Copus hands macOS the list of what a task may write and read, and macOS applies that list to the program it starts and to everything that program starts after it: a file tool, a command, a script Copus wrote and ran, a helper that script launched. macOS holds this boundary whatever program runs inside it.

This page covers how to:

- [Find the folders a task can write to](#what-a-task-can-write), and the few places outside them
- [Learn which filenames no task can write](#files-no-task-can-write), anywhere on your Mac
- [See what a task can read](#what-a-task-can-read), and which folders stay shut
- [Open a shut folder](#open-a-shut-folder) that a tool needs, such as `~/.aws`
- [See which websites a command can reach](#websites-a-command-can-reach), and when Copus asks you
- [Understand why writing is confined and reading is not](#why-copus-confines-writing-and-not-reading)
- [Let a project or AI team work on code](#work-on-code), and run commands outside the sandbox
- [Know where the sandbox stops](#where-the-sandbox-stops), and what covers the rest

<Note>
  Copus starts a task only when macOS can apply the sandbox to it. If macOS can't, Copus refuses to start the task.
</Note>

## What a task can write

A task writes inside its own folder, which depends on where the task sits. A conversation can also write in the folders you add.

- A conversation outside a project writes inside its own workspace folder, and your other files stay as they are. A task Copus starts on its own writes inside its own workspace folder in the same way.
- A conversation in a project writes anywhere inside that project's folder, because tasks in a project are meant to build on each other's files. For a project you pointed at a folder of your own, that means your folder. Copus creates files in it, and writes over files you already had.
- A conversation also writes inside each folder you added to it or to its project. See [Add a folder Copus can change](/concepts/sessions-and-workspace#add-a-folder-copus-can-change).
- A scheduled task writes inside a folder of its own, shared by every run. A scheduled task never gets a folder you added.

To find where each folder sits on disk, see [Tasks and the workspace](/concepts/sessions-and-workspace).

A task can also write to a few places outside its folder. Copus gives each task a temporary folder of its own for scratch work. A task can't write to the Mac's shared temporary folders, such as `/tmp`. Claude Code and Codex each keep a configuration folder, where they write state as they run and renew their own sign-in. Copus's browser keeps two folders, one holding the logins for sites you have signed in to and one holding its own working files. Copus leaves the browser program itself unwritable, so a task can't replace the program that browses for it.

<Note>
  Copus points Python's package installer at a `.python` folder inside the task's own boundary, so a task can install a package it needs and the install lands where its other files land.
</Note>

## Files no task can write

Copus blocks writes to these filenames everywhere, including inside the folder a task can otherwise write freely:

- `copus.db`, `copus.db-wal`, and `copus.db-shm`, the files of Copus's own database.
- `settings.json`, `settings.local.json`, and `CLAUDE.md`, which Claude Code reads when it starts. A task that could rewrite any of those files could hand itself permissions or standing instructions on its next run, so Copus blocks every write to them.

macOS matches those names on the filename alone, wherever the file sits. The rule covers every copy. A task can't create a file of its own called `settings.json`, even in its own folder. A task that tries gets an error.

## What a task can read

A task reads its own folder, the files you attach, and the folders you added to it. A task in a project also reads the project's folder, the folders you added to the project, and its sources. Every task can also read the files other tasks made. Every task also reads the folders on your **Folders Copus can read** list, and can't create, change or delete files in them. That list starts with your Desktop, Documents, Downloads and Pictures folders, and holds up to 20 folders. To change it, open the list: In **Settings**, select **Built-in tools**, then select the number of folders under **Read files**, such as "4 folders". Select **Add folder** to add a folder, or select **Remove folder** beside one, then **Remove**, to take it off. Copus applies the change to each task from that task's next message. macOS shuts the rest of your home folder, such as `Movies`, `Library`, and the hidden folders whose names start with a dot. To let every task read another folder, such as `~/.config` or a folder outside your home folder, add it to the **Folders Copus can read** list. To let one task also change the files in a folder, [add the folder to that task or its project](/concepts/sessions-and-workspace#add-a-folder-copus-can-change). Outside your home folder, a task reads the system and the programs you installed, but not other drives or the `/Users/Shared` folder unless you add them. Copus reads without asking, and you can't set reading to ask.

macOS shuts these folders in your home folder to a task and to every process it starts: `.ssh`, `.aws`, `.azure`, `.gnupg`, `.kube`, `.docker`, `.gradle`, `.m2`, `.huggingface`, `.kaggle`, and `.config/gcloud` and `.config/gh`, the settings folders for the `gcloud` and `gh` command-line tools. macOS also shuts your keychain folder, `~/Library/Keychains`, which names every password your Mac keeps.

macOS shuts these files in your home folder too. `.netrc`, `.npmrc`, `.pypirc`, and `.git-credentials` hold credentials outright. Your shell startup files, `.zshrc`, `.zshenv`, `.bashrc`, `.bash_profile`, and `.profile`, routinely hold an exported API key.

macOS also shuts Copus's own database, under a separate rule.

<Note>
  macOS binds the block to every process the task starts, as well as to Copus's own tools. A task can't get around it by asking a command-line tool to print a key.
</Note>

macOS also shuts a file that looks like it holds a password, anywhere on your Mac outside a folder you [opened by name](#open-a-shut-folder): an `.env` file, a `.pem` or `.key` file, an `id_rsa` key file, or a file named `credentials`, `credentials.json`, `auth.json`, or `secrets.yaml`. Copus refuses a task's read of one in every approval mode, without asking you. Copus reads a template such as `.env.example`, `.env.sample`, or `.env.template` as an ordinary file. Copus asks you every time, in every approval mode, before a task reads the sign-ins Copus keeps in `CopusData`, such as the sign-ins you make in Copus's browser. For every name, and for what happens when nobody is there to answer, see [Approvals and permissions](/control/approvals-and-permissions).

<Warning>
  The shut folders and files are the places credentials usually sit. A secret can live in a file with any name, in any folder, so the list can't cover every secret. The list stops a task from reading a token by accident while it looks around. Treat the list as a guard against accidents rather than as a guarantee.
</Warning>

### Open a shut folder

Some command-line tools need their credential folder, such as the `aws` tool, which reads your keys from `~/.aws`. A shut folder opens for a task when you add that folder by name, or a folder inside it, to your **Folders Copus can read** list, to the conversation, or to its project or AI team. Every program the task runs can then read the files in it. On your **Folders Copus can read** list the folder opens for reading only. Added to a conversation, project or team, the folder also lets a task change its files.

Inside a folder you opened, the files that look like passwords open too. When a task reads one with a file tool, or names it in a command such as `cat ~/.aws/credentials`, Copus asks you first, every time, in every approval mode. With nobody there to answer, Copus refuses. Copus reads the folder's other files, such as `~/.aws/config`, without asking. A program that reads the file on its own, such as `aws`, gets no question.

A broader folder you add keeps the shut places inside it shut, at both sandbox levels: the credential folders and files this page names, other tools' and AI tools' sign-ins, the cookies and storage apps and browsers keep in `Library`, and your shell history. Add `Library` and your keychain folder and Slack's sign-in stay shut. Add `~/.config` and the sign-in folders of tools such as `gcloud` and `gh` stay shut. To open one of those places, add it by name. Copus's own app folder in `Library` stays shut too, and you can't add it.

<Warning>
  A folder on your **Folders Copus can read** list opens for every task, including scheduled tasks and AI teams. Put a credential folder such as `~/.aws` on that list only if every task may use those keys. To open it for one conversation, add it to that conversation instead.
</Warning>


## Websites a command can reach

A command a task runs, and every program that command starts, reaches the internet only through Copus. macOS blocks every other connection off your Mac, apart from the [certificate checks a plugin can open](#where-the-sandbox-stops) to its own programs. Copus lets these sites through without asking, in every mode:

- Your AI provider's own sites.
- The sites Python and Node packages come from.
- Copus's own website and documentation.
- A site you allowed for this conversation, and a site you approved for a scheduled task or an AI team.

For any other site, Copus asks you first, with a request that names the site. Select **Allow once** to let the command reach the site this time. To let the conversation reach that site from then on, select the button that names it, such as **Allow api.example.com for this conversation**. Select **Don’t allow** to refuse it. On **Full access**, Copus lets every site through without asking. In work Copus runs with nobody watching, Copus refuses any site nobody approved, whatever the mode.

## Why Copus confines writing and not reading

A task has to read your own material to do your work. A document you attached to a message, a spreadsheet in your Downloads folder, and a report in your Documents folder all sit outside the task's own folder. If Copus confined reads to that folder, a task could write files and still couldn't read the files you asked it about. So every task can read the folders on your **Folders Copus can read** list, which starts with your Desktop, Documents, Downloads and Pictures folders. You decide which folders are on that list.

Copus puts each limit where a task could do damage. Writing is where a task can destroy something, so Copus confines writing to the task's own folder and the folders you add. Reading is where a task can leak something, so macOS shuts the rest of your home folder, the credential folders, and the files that look like passwords.

## Work on code

**Sandbox level** is a setting on a project or an AI team that decides how much of your Mac its tasks can read. **Standard** is the sandbox the rest of this page describes, and every project and team starts on it. **Coding** lets tasks read files across your Mac, apart from the places that hold passwords, keys and sign-ins. Choose **Coding** for a project whose tasks write, build or test code. Coding tools keep their installs, caches and settings in your home folder, which **Standard** keeps shut. At either level, tasks can also run the commands on the project's or team's [**Allowed outside the sandbox**](#allowed-outside-the-sandbox) list.

To change the level, open the project's **Settings** in the top bar, or the team's **Settings** panel, and choose under **Sandbox level**. Only you can change it, in Copus on your Mac. The level covers every task in the project or team.

At **Coding**, a task reads your whole home folder, including `Library`. macOS still shuts:

- Your credential folders and files, such as `.ssh`, `.aws` and your keychain folder, as at **Standard**.
- Other tools' sign-in files, and your shell history.
- The cookies, saved sign-ins and private data of your browsers and other apps, such as your mail and messages.
- Other AI tools' sign-ins and conversations, and Copus's own data folders.
- Other drives.

As at **Standard**, a shut place opens when you add it by name. See [Open a shut folder](#open-a-shut-folder). Writing doesn't change.

<Warning>
  The list of shut places can't name every tool's sign-in file. A task at **Coding** can read a secret kept anywhere the list doesn't reach, and Copus sends whatever a task reads to your AI provider. Set **Coding** only on a project or team whose work needs it.
</Warning>

### Run a command outside the sandbox

At **Coding**, Copus can ask you to run one command outside the sandbox, such as a build that writes outside the task's folders or a `git push` that needs your sign-in. Copus shows you the exact command and the folder it runs in. Select **Run** to run it once, or **Don’t run** to skip it. You answer only in Copus on your Mac.

A command you run this way has full access to your Mac, like a command you type in Terminal. It can also run files Copus wrote or changed in that folder, such as a project's scripts and tests. Read the command and the folder before you select **Run**.

### Allowed outside the sandbox

A project or AI team can keep a list of commands its tasks may run outside the sandbox with no card, called **Allowed outside the sandbox**. Use it for the builds and tests an AI team needs while nobody is there to select **Run**, or for a command a project's conversations run often. The list sits in the project's **Settings**, or the team's **Settings** panel, under **Sandbox level**. Copus uses it at both levels, **Standard** and **Coding**.

You add a command to the list in one of three ways:

- On a card for a command outside the sandbox, select **Always allow in this project**, or **Always allow in this team**. Copus runs the command and adds it to the list. The card shows exactly what the button saves: the command up to its first option, with arguments allowed after it, or, when cutting would leave too little, the whole command exactly. An option is a word that starts with `-`, such as `--grep`.
- Select **Add command** under the list and type the command. To run it in a folder other than the one shown, paste the folder's path or select **Choose…**. Then select **Add command**.
- In an AI team, the team can ask for a command under **Needs you**, or list one in its requirements. Approving the request or the requirements adds it.

Copus keeps some commands off the list: one it always refuses or asks about every time, such as `git push`, one that reads a password file or a folder it keeps shut, and one it can't read in full, such as a command holding `$( )`. A card for one of these has no button to always allow it, and the **Add a command** window says why it can't join the list.

Each row on the list holds one command and the folder it runs in. The command runs in that folder or any folder inside it. Turn on **Allow arguments** to let a task add plain words after the command, called arguments, such as a test file's name or an option. The row then shows **Arguments allowed**. With it on, a row for `npx playwright test` also covers `npx playwright test e2e/login.spec.ts`. Each file must be named in full, with no `*`, `~` or `$`. Copus never counts words that chain another command or redirect output, and it checks the whole command again every time it runs, so a row for `git` with arguments allowed still never runs `git push`. Copus refuses arguments after a command that runs whatever program it is given, such as `bash -c`, `npm exec` or `go run`. It also refuses them after a command that installs packages, such as `npm install` or `pip install`, because every package it names can run its own scripts.

Select a row to open it. There you can turn **Allow arguments** on or off, or select **Remove** to take the command off the list. Copus stops a run of that command if one is going.

A command on the list runs with no card whether or not you're there, and the conversation shows it running with **Approved for** and the project's or team's name. With nobody there, Copus refuses every other command outside the sandbox. In an AI team, a teammate whose command Copus refused reports it to the team lead. The team lead asks you to approve the command under **Needs you**, and the teammate runs it once you do. When Copus can't put the command on the list, the team lead asks you to run it yourself. At **Standard**, Copus never shows the card, so a task can run only the commands on the list. A scheduled task sits outside every project, so its runs never use a list.

<Warning>
  A command on the list runs with full access to your Mac and no card, even in a team with nobody watching. A test or build command runs whatever the project's files tell it to, and the project's tasks can change those files. Add only commands you would run yourself in that folder.
</Warning>

## Where the sandbox stops

The sandbox controls where a task may write and what it may read. It also keeps a task away from your keychain and your other apps. A task can't ask macOS for a keychain value, open or control another app, read the clipboard, use the microphone, read your Mac's Calendar or Reminders, ask for your location, or start a program that keeps running after the task. It also can't stop a program it didn't start, such as one of your apps, Copus itself, or another task. It can't mount, unmount or eject a disk, run one of your Shortcuts, or use the SSH keys your Mac's SSH agent holds. The cases below fall outside the sandbox.

**A command can send what it reads to a site Copus lets through.** Copus doesn't check what a command sends. A command can upload any file its task can read to any site on the [list of sites Copus lets through](#websites-a-command-can-reach), or, on **Full access**, to any site. Copus also asks before every command outside its read-only list, which is why you can't set **Run commands** to run on its own. On **Autopilot** and **Full access**, Copus runs the command without asking.

**A refused write fails quietly.** macOS refuses the write and hands the task an error. Copus doesn't ask you about the write, so you can't approve it by mistake. Copus either reports the failure in its reply or works around it.

**One task can read another task's files.** A task can read the files any other task made, so treat anything a task produced as visible to a later task. It can't change them unless both tasks are in the same project.

**Tasks in the same project can write each other's files.** They share the project folder by design. A task outside a project can still read another task's files, and can't write them. Two conversations you added the same folder to can both write in it.

**A command you approve to run outside the sandbox has no sandbox.** A command you approve with **Run**, and a command on a project's or team's **Allowed outside the sandbox** list, runs with full access to your Mac and reaches any website. See [Allowed outside the sandbox](#allowed-outside-the-sandbox).

**A plugin you approve can open your keychain or certificate checks to its own programs.** When Copus runs a plugin's own Claude Code, the programs that plugin names can use your Mac's keychain, or check a website's certificate through macOS, and a certificate check can reach websites outside the list Copus lets through.

**A key you hand a program yourself can be read.** A task can read the settings any program on your Mac started with, so a key you export in a Terminal window is readable while that program runs. You can use [Secrets](/connections/secrets) to securely store and use passwords, tokens, and API keys in Copus.

**Copus protects a stored credential by other means.** Copus keeps the value out of the conversation. See [Secrets](/connections/secrets).

<Note>
  Skills are the packaged instructions Copus follows for particular kinds of work. A task can read and follow a skill from anywhere, and can never rewrite it.
</Note>
